# 周报数据弹性方案分析

> 背景：周例会营销材料依赖 Excel 数据源，但 Excel 结构易变。需评估如何让数据提取具备弹性。

---

## 核心问题

**传统方式**："长江电力在第5行第3列"
- 结构变了 → 位置错 → 数据错
- 脆弱性高

**目标**："找'长江电力'这个实体，它有'水电电量'属性"
- 不关心位置，只关心语义
- 结构变了 → 重新解析 → 语义标签存在就正确

---

## 方案梯度对比

| 方案 | 弹性 | 成本 | 维护 | 场景 |
|-----|------|------|------|-----|
| 硬编码位置 | 无 | 最低 | 无 | 结构永不变 |
| Schema 校验 | 发现变化 | 低 | 低 | 告知变化 |
| 配置驱动 | 改配置 | 中 | 配置维护 | 可控变化 |
| 语义定位 | 较高 | 中低 | 词典维护 | 表头稳定 |
| 知识图谱 | 最高 | 高 | Ontology 维护 | 多源/复杂推理 |
| LLM 辅助 | 最智能 | 高 + API 费 | 几乎无 | 任意格式 |

## 知识图谱方案

### 概念模型

```
实体类型：
├── Organization（组织）：长江电力、三峡能源、湖北能源
├── EnergyType（能源）：水电、风电、光伏、火电
├── Metric（指标）：电量、电价、电费
├── Region（区域）：国内、国际
└── Week（时间）：第21周

关系类型：
├── Organization → HAS_ENERGY_TYPE → EnergyType
├── Organization → HAS_METRIC → Metric
├── EnergyType → HAS_METRIC → Metric
└── Metric → VALUE → 数值

实例：
├── 长江电力:Organization
├── 长江电力 HAS_ENERGY_TYPE 水电
└── 长江电力.水电 HAS_METRIC 电量 → VALUE: 550544.26
```

### 解析流程

```
Excel 输入 → 语义解析 → 图谱构建 → 图谱查询 → 数据输出
```

### 对结构变化的弹性

| 变化类型 | 传统方式 | 知识图谱 | 备注 |
|---------|---------|---------|------|
| 列顺序变 | 错误 | 正确 | 找"水电"标签在哪列 |
| 新增"备注"列 | 偏移错误 | 正确 | 只识别已知实体 |
| 表头改名"水电"→"水力发电" | 找不到 | 需同义词 | 扩展 ontology |
| 行顺序变 | 错误 | 正确 | 找"长江电力"在哪行 |
| 新增组织 | 无数据 | 需扩词典 | 正常扩展 |
| 合并单元格/多层表头 | 无法处理 | 需特殊解析 | 增强解析器 |

### 知识图谱优点

1. 语义理解而非位置依赖
2. 领域知识沉淀
3. 推理能力（复杂查询）
4. 多源融合

### 知识图谱挑战

1. 技术成本（Neo4j、ontology、语义解析器）
2. 维护成本（实体词典、关系类型、同义词）
3. 边界情况（合并单元格、自由文本、多层表头）
4. 可能过度设计（单一 Excel 场景）

## 轻量语义定位方案

对于这个场景，轻量级语义定位可能解决 80% 问题。

### 核心代码示例

```python
# 实体词典
ORG_LIST = ["长江电力", "三峡建工", "三峡能源", "湖北能源"]
ENERGY_TYPES = ["水电", "风电", "光伏", "火电"]
METRICS = ["电量", "电价", "电费"]

# 同义词映射（应对表头变化）
SYNONYMS = {
    "水力发电": "水电",
    "上网电量": "电量",
    "平均电价": "电价",
}

def smart_parse(ws):
    # 找组织名所在的行
    org_rows = {}
    for row_idx, row in enumerate(ws.iter_rows()):
        for cell in row:
            text = str(cell.value) if cell.value else ""
            for org in ORG_LIST:
                if org in text:
                    org_rows[org] = row_idx
    
    # 找表头列
    header_row = find_header_row(ws)
    col_mapping = {}
    for col_idx, cell in enumerate(header_row):
        header_text = str(cell.value) if cell.value else ""
        for energy in ENERGY_TYPES:
            for metric in METRICS:
                energy_key = SYNONYMS.get(energy, energy)
                metric_key = SYNONYMS.get(metric, metric)
                if energy_key in header_text and metric_key in header_text:
                    col_mapping[(energy, metric)] = col_idx
    
    # 提取数据
    data = {}
    for org, row_idx in org_rows.items():
        data[org] = {}
        for (energy, metric), col_idx in col_mapping.items():
            val = ws.cell(row=row_idx, column=col_idx+1).value
            data[org][energy] = {metric: val}
    return data
```

这本质是**知识图谱的简化版**：
- 实体词典 = ORG_LIST + ENERGY_TYPES + METRICS
- 关系推断 = 通过表头组合判断
- 不需要 Neo4j、不需要复杂 ontology

## 知识图谱真正发挥价值的场景

| 场景 | 知识图谱价值 |
|-----|-------------|
| 多数据源融合 | Excel + API + 数据库 → 统一查询 |
| 复杂推理 | "长江电力电价下降原因？" → 推理链 |
| 知识问答 | "上周谁电价最高？" |
| 趋势分析 | 跨周数据关联、异常检测 |
| 组织关系 | 长江电力隶属三峡集团、湖北能源控股... |

单一 Excel 数据提取，可能**轻量方案就够了**。

## 分层策略

```
┌─────────────────────────────────────────────────────┐
│ Level 0: 实体词典（必须做）                          │
│ ├── 组织词典: ORG_LIST                              │
│ ├── 能源词典: ENERGY_TYPES                          │
│ ├── 指标词典: METRICS                               │
│ └── 同义词映射: SYNONYMS                            │
│ → 解决 80% 结构变化问题                              │
└─────────────────────────────────────────────────────┘
           ↓
┌─────────────────────────────────────────────────────┐
│ Level 1: 语义定位解析器                              │
│ ├── 词典匹配找位置                                  │
│ ├── 表头智能识别                                    │
│ └── 输出结构化 JSON                                  │
│ → 无需知识图谱，已有语义弹性                        │
└─────────────────────────────────────────────────────┘
           ↓
┌─────────────────────────────────────────────────────┐
│ Level 2: 知识图谱（可选增强）                        │
│ ├── 多数据源需求时投入                              │
│ ├── 复杂推理需求时投入                              │
│ └── Neo4j 存储、高级查询                            │
│ → 未来扩展，非必须                                  │
└─────────────────────────────────────────────────────┘
           ↓
┌─────────────────────────────────────────────────────┐
│ Level 3: LLM 辅助（终极弹性）                        │
│ ├── 词典无法识别时调用                              │
│ ├── "这列是什么指标？" → LLM 判断                  │
│ └── 处理完全陌生的格式变化                          │
│ → 最智能，但有 API 成本                            │
└─────────────────────────────────────────────────────┘
```

## 待讨论的关键问题

### 1. 知识图谱必要性

未来是否多数据源需求（API、数据库）？
- 仅 Excel → 轻量语义定位够用
- 多数据源 → 知识图谱真正发挥价值

### 2. Excel 实际痛点场景

Excel 结构变化具体是什么？
- 仅行列顺序变 → 语义定位可解
- 表头命名会变 → 需同义词映射
- 新增/删除指标 → 需扩展词典
- 完全重构格式 → 需 LLM 辅助

### 3. 维护成本权衡

谁来维护实体词典/知识图谱？
- 知识图谱需维护 ontology
- 词典只需维护实体列表
- 团队有维护能力和意愿吗？

### 4. LLM 角色

是否考虑 LLM 做语义理解？

| 场景 | 词典 | 知识图谱 | LLM |
|-----|------|---------|-----|
| 表头改名 | 报错需人工 | 报错需人工 | 自动判断 |

### 5. 未来扩展需求

除数据提取外还有其他需求吗？
- 仅提取数据 → 语义定位够用
- 问答系统 → 知识图谱有价值
- 异常推理 → 知识图谱有价值
- 跨周趋势 → 图谱有帮助

## 推荐路径

```
推荐实施顺序：
├── 立即做：实体词典 + 语义定位解析器
│   → 成本低，解决 80% 问题
│
├── 观察后再做：知识图谱
│   → 等多数据源/复杂推理需求时投入
│   → 现在可能过度设计
│
└── 备用方案：LLM 辅助
    → 词典无法识别时调用
    → 最弹性但最贵
```
